## 2. 性能测试结果

### 2.1 带宽测试

| 测试项 | 理论峰值 | 实测峰值 | 利用率 |
|--------|----------|----------|--------|
| PCIe H2D | 15.75 GB/s | **5.34 GB/s** | 33.9% |
| PCIe D2H | 15.75 GB/s | **4.63 GB/s** | 29.4% |
| HBM D2D (memcpy) | 512 GB/s | **65.9 GB/s** | 12.9% |

- PCIe 瓶颈在 **DMA 引擎设计吞吐**，与 PCIe 代数无关
- HBM memcpy 带宽低不代表真实 HBM 带宽，GEMM 场景有效带宽估算约 40-50 GB/s

### 2.2 计算吞吐

**FP32 GEMM:**

| 矩阵规模 | GFLOPS | 延迟 |
|----------|--------|------|
| 512×512×512 | 2,500 | 0.11 ms |
| 1024×1024×1024 | 5,800 | 0.37 ms |
| **2048×2048×2048** | **7,800** | **2.20 ms** |
| 4096×4096×4096 | 4,500 | 30.6 ms |
| 8192×8192×8192 | 4,500 | 243.7 ms |

- 峰值: **7.8 TFLOPS** @2048³
- vs 理论 16 TFLOPS: **利用率 48.9%**
- 大矩阵 (K>2560) 性能腰斩至 4.4 TFLOPS

**FP16 GEMM** (TGEMM=short, 内部 float32 累加):

| 矩阵规模 | GFLOPS | 延迟 |
|----------|--------|------|
| 512×512×512 | 3,300 | 0.08 ms |
| 1024×1024×1024 | 13,000 | 0.17 ms |
| 2048×2048×2048 | 20,100 | 0.86 ms |
| **4096×4096×4096** | **22,600** | **6.07 ms** |
| 8192×8192×8192 | 18,200 | 60.2 ms |

- 峰值: **22.6 TFLOPS** @4096³
- vs 理论 64 TFLOPS: **利用率 35.4%**
- 比 FP32 稳定 — K 维度 1024~4096 几乎无性能下降

**INT8 GEMM**: 不可测。XDNN 2.0.0.725 无 `<int8,int8,int8,int8>` 模板实例化，底层 `fc_int8_v1` 符号存在但固件无对应 CDNN kernel。

### 2.3 K 维度扫描 (M=N=2048)

| K | FP32 GFLOPS | FP16 GFLOPS | 现象 |
|---|-------------|-------------|------|
| 128-2048 | ~7,300 | ~17,500 | 稳定 |
| 2048-2560 | 7,800→6,100 | 19,900→18,600 | FP32 开始衰减 |
| 2560-3584 | 6,100→4,200 | 18,600→19,000 | **FP32 寄存器溢出** |
| 3584-8192 | ~4,400 | 19,000→14,700 | FP32 触底; FP16 K>4096 也溢出 |

FP16 不溢出的 K 范围 = 2.0× FP32 → 精确对应 float16(float32) 的字节数比。

### 2.4 Paddle 推理

| 模型 | Batch | 吞吐 | 延迟 |
|------|-------|------|------|
| ResNet-50 (FP32) | 1 | 1,069 img/s | 0.94 ms |

## 3. 根因分析

### 3.1 不是带宽瓶颈

所有 GEMM 配置的所需带宽均 < 30 GB/s，远低于实测 memcpy 66 GB/s。Roofline 分析全部落在 compute-bound 区。

### 3.2 不是纯算力瓶颈

FP16 可达 22.6 TFLOPS，说明 CDNN 计算单元本身有产出能力。FP32 性能低是 kernel 实现质量问题。

### 3.3 真正瓶颈：CDNN 寄存器文件容量

- K200 CDNN 单元每个 tile 的寄存器文件有限
- FP32 GEMM 在 K>2560 时，寄存器装不下完整 K 子块 → 溢出到 L2/HBM → 性能腰斩
- FP16 寄存器占用减半，溢出边界推到 K>4096
- 这是硬件微架构的固有限制，无法通过软件优化突破
- 结论：**K200 以 FP16 为主要设计目标，FP32 是"也能跑"的副产物**

### 3.4 INT8 不可用的根因

```
xdnn::fc<int8_t,int8_t,int8_t,int8_t>  → 模板实例化不存在 → err=1
::fc_int8_v1<int8_t,int8_t,int8_t>     → 链接成功         → 固件无 kernel
```

K200 固件 (0001.0016.0021/0022) 不含 INT8 GEMM CDNN kernel。这是固件层缺失，与 XDNN 版本无关。

### 3.5 K200 历史定位

- 2020 年量产，百度搜索/推荐/小度等业务大规模部署（数万片）
- 以 **FP32 推理** 为主要工作负载（搜索排序模型对精度敏感）
- INT8 在产品化阶段优先级低，到 2022 年大模型兴起时，昆仑 2 代已推出
- XDNN 2.0.0.725 (2024-04-29) 为 XPU1 最终公开 SDK，此后进入维护模式
- vLLM-Kunlun (2025-12) 仅支持 XPU3/P800

## 4. 应用场景评估

| 应用 | 可行性 | 说明 |
|------|--------|------|
| **AI 降噪/超分** | ✅ 推荐 | GEMM/Conv 密集，FP16 友好，离线批处理够快 |
| **图像生成 SD 1.5** | ✅ 可做 | 需手写 XDNN UNet，512² 约 3s/张，内存可装 |
| **图像生成 SDXL** | ⚠️ 勉强 | 模型 3.5GB，内存偏紧，推理 7-15s |
| **图像生成 Flux** | ❌ | 模型 17GB，无法装入 8GB HBM |
| **LLM 推理 (小模型)** | ⚠️ 勉强 | Attention 可做，8GB 只能装 ~3B 模型 (FP16) |
| **NeRF (MLP-based)** | ✅ 可行 | MLP = GEMM 密集，FP16 高效 |
| **3D Gaussian Splatting** | ❌ | Tile rasterizer 不规则计算，XDNN 无对应 API |
| **实时渲染** | ❌ | PCIe 延迟 + 无图形管线 |
| **大模型训练** | ❌ | 显存/带宽/生态均不支持 |
| **视频生成** | ❌ | 模型 > 8GB，时序计算量过大 |

## 5. 开发建议

### 如果继续使用 K200

1. **所有推理切 FP16**: 比 FP32 快 2-5×，精度足够（内部 float32 累加）
2. **控制矩阵 K 维度**: FP32 避免 K>2048，FP16 避免 K>4096
3. **小 batch 推理**: 利用 batch 摊销 kernel launch 开销
4. **模型 ≤ 6GB**: 留 2GB 给中间张量和 workspace
5. **使用 PaddlePaddle 3.0 dev**: `paddlepaddle_xpu-3.0.0.dev20240630` 支持 AMP 混合精度
6. **手写 XDNN**: 对性能敏感路径绕过 PaddlePaddle，直接调 XDNN API

### 如果要升级硬件

| 升级目标 | 解锁能力 |
|----------|----------|
| XPU2 (R200/R300) | INT8 GEMM、更高 FP16 利用率、P2P 通信 |
| XPU3 (P800) | vLLM 全栈、W8A8/FP8、96GB HBM、大模型推理 |

### 不要做的事

- 不要在 K200 上训练模型（显存太小，无分布式通信）
- 不要期望跑通 PyTorch 生态（唯一入口是 PaddlePaddle + XDNN）
- 不要试图写自定义 CDNN kernel（工具链不公开）
- 不要做实时应用（PCIe 带宽和延迟限制）
- 不要期待更多 SDK 更新（XPU1 已进入维护末期）
